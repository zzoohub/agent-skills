# Tools & Agents

Decides how a model acts through tools: the harness around the loop, the tool surface, interop seams, multi-agent admission, durable runs and oversight mechanics. Read when the shape chosen in `ai/protocol.md` gives a model tools or an agent loop; authority and containment live in `ai/security.md`, budgets and caps in `ai/production.md`.

## The model proposes, code disposes

- **Judgment only.** The model owns only the decisions that need judgment over ambiguous input (`ai/protocol.md`); sequencing, policy limits, permissions, budgets and compliance steps stay in deterministic code, and the loop never executes a proposal itself: code decides — execute, pause for approval, reject, or stop on budget — and every effect passes the policy-enforcement point outside the model (`ai/security.md`). *Break when* the investigation is open-ended and differs per input, so encoding the path would grow an unmaintainable rules engine — that is where an agent pays.
- **Agent = model + harness.** For each material failure mode, name the *guide* that prevents it (instruction, tool constraint, template, example) and the *sensor* that detects it. Prefer computational sensors on every step — schema and type validation, tests, invariant and structural checks, deterministic replay; use inferential ones (a model reviewer or judge) only for semantic properties, and only once validated (`ai/evals.md`). Forcing question: when the agent is wrong, what tells it, how fast, how deterministically? *Break when* the feature is a single call (classify, extract, summarize): output validation plus evals, no harness.
- **Harness subsystems — specified or inherited?** For the loop, model access, tools, context policy (truncation, compaction), permissions and sandbox, sub-agent orchestration, and extensibility (plug-ins, skills, hooks), record whether the behavior is designed or a framework default. Keep the loop thin and owned, and write it with direct model calls before adopting a framework. *Break when* a framework or managed runtime supplies an operational capability you would otherwise build and run (durable execution, approval plumbing): adopt it, keeping context policy, permissions and state explicit and testable.
- **Decision-tier gates.** The harness's own control decisions — model choice at run start, a risk check on each proposed tool call, per-turn screening, narrowing the tool list, stop or continue — go to a decision tier (`ai/protocol.md`), leaving planning and generation to the generative model. Gates fail closed (block or ask), sit in front of server-side authorization and never replace it, and have defined behavior when the decision service is slow or down. *Break when* the check needs reasoning over the whole trajectory, the gate reads attacker-controlled text and is the only defense (decision flips → `ai/security.md`), or its round trip breaks the latency budget.

## Tools

- **Task-shaped, few, disjoint.** One tool per agent task, not per API endpoint: consolidate chains of primitive calls and namespace related tools. A human engineer can say which tool applies, and each description says when to use it and when not. Constrain arguments — enums, typed and human-meaningful identifiers, bounded ranges — so whole classes of mistakes are impossible, with usage examples for complex parameters. One tool multiplexed by an "action" parameter blurs selection; a single free-form query or shell tool puts the entire safety burden on the model.
- **Outputs spend the context budget.** Return high-signal, token-bounded results: concise and detailed response modes, pagination, truncation with a hint on how to narrow. Tool output is untrusted input (`ai/security.md`).
- **Errors return as errors, recoverable:** a code, a message and a suggestion for fixing the call (e.g. `USER_NOT_FOUND` · "no user with id u_123" · "use search_users to find the id") — never an error string the agent can mistake for data, nor a raw stack trace. Quiet failures compound: serial chains multiply step reliability, so 90%-reliable steps give 5 ≈ 59% and 10 ≈ 35% (0.9^n). Mitigate with structured orchestration, verification after critical actions by a component other than the producer, feedback grounded in the environment (tests, validators — not self-critique in the same context), and fewer serial dependencies (parallelize independent reads). Each tool call gets a deadline from the run's remaining budget and returns a clear timeout error.
- **Change the surface only for an observed bottleneck.** Definitions crowd the context or overlap → load tools on demand behind a small always-loaded core (judge overload by overlap, not count) before splitting into separate agents; malformed calls → usage examples. *Break when* a few compact tools serve every task: load them up front.
- **Code as the action layer.** When a task fans out over many items, chains several dependent calls, or moves bulky intermediates the model need not read, let the model write an orchestration program that a sandboxed, deterministic runtime executes, returning only aggregates; verify independently before merging results. Fan-out has spend and concurrency caps (`ai/production.md`), and generated code passes the same action-permission gates as direct tool calls. *Break when* every intermediate result should inform judgment, or the task is small or latency-critical: keep the plain tool loop.
- **Prefer a structured tool or API to driving a GUI** — cheaper, faster, more reliable and easier to permission; GUI and browser agents are the long tail, isolated per `ai/security.md`.
- Tool names, descriptions, schemas and their order belong to the release unit (`ai/evals.md`) and to the cache prefix (`ai/production.md`).

## Interop seams

- **Three seams:** agent ↔ tools, agent ↔ agent, agent ↔ user. Decide per seam whether you need interoperability at all; keep any interop protocol behind an adapter, since specs evolve, and own the event and data schemas in your codebase.
- **In-app tool calls by default:** tools coupled to your authorization, data and business logic stay inside your trust boundary. Adopt a tool protocol only when hosts you do not control must consume your tools (expose a server) or users must plug in their own tool servers (act as a host). An agent-facing interface to your product is a published contract (`design-flow.md` § Published Contracts).
- **Tool vs peer agent:** a tool when the caller wants a bounded, structured result; a peer agent over an agent-to-agent protocol only across an ownership, organizational or trust boundary. Never put a network protocol between components that share a codebase and trust domain — call them in-process.
- **Remote tool-protocol servers are ordinary stateless services** where the protocol version and features in use allow it (verify its session model at design time): no sticky sessions or shared session store; long-running tool work becomes a task with durable state and status and cancel operations, not a held-open stream; state lives only in server-minted handles bound to the principal; tool listings are deterministic. Each server is a resource server — audience-bound tokens, its own credentials downstream, the inbound token never passed through; a locally launched server takes credentials from its environment, so scope the environment. Details, and third-party servers as executable dependencies → `ai/security.md`.

## Multi-agent admission & rules

Default: one agent, using sub-agents only to isolate context — they read, search or review and return condensed results or artifact references. Admit multiple agents only when **all** hold:
- a hard boundary exists (security or compliance isolation, separately owned domains), **or** the work splits into independent breadth-first branches — or exceeds one context window — where a single agent scores poorly;
- the token multiplier is budgeted and compared at equal compute, against a token-matched single-agent baseline;
- the gain shows on your own eval, and a measured verifier can tell good worker output from bad;
- exactly one agent, or code, writes each artifact that can change — parallelize reading, serialize writing;
- an aggregator validates worker output centrally before merge, and output crossing a trust boundary is untrusted data;
- the orchestrator scales effort — workers and calls per task — with task complexity, under the run budget (`ai/production.md`).

Once admitted:
- **Shape.** Role names never qualify; a "role" that maps to a real permission or data difference (a quarantined reader) is a security split. Structure fleets as a hierarchy (planner, workers, judge), never as peers coordinating through shared locks or an unarbitrated shared store; when the right handler is predictable from the input, dispatch deterministically instead of by model handoff. *Break when* write targets are truly disjoint and a mechanical oracle (locks plus near-complete tests) arbitrates.
- **Delegation.** Every delegation carries a brief (objective, output format, sources and tools, boundaries); escalation to a stronger tier fires on an external, objective trigger, never on the cheaper model's own judgment.
- **Where it pays.** Breadth-first search and research; it most often loses on sequential planning and where one agent already scores well.

## Runs: separable, durable, resumable

- **Separate the loop, the executors and the session log.** The log is the source of truth (`ai/context.md`); the loop is stateless; executors (sandboxes, browsers, workers) are disposable. Credentials stay outside executors, applied by a proxy bound to the session's principal (`ai/security.md`). Forcing questions: what is lost if the executor dies mid-task, or the loop process does? Whose credentials does each tool call carry? *Break when* a local single-user tool couples loop and executor, or a sub-minute request/response feature needs no persistence.
- **Durable execution — agent deltas** on `operational-patterns.md` § Durable Execution: model and tool calls are non-deterministic steps whose results are persisted — replay re-reads them, never re-invokes; the checkpoint includes context and plan state; a side effect executed before a durable pause may run again on resume, so it carries an idempotency key or records completion first; an in-flight run resumes on the code, prompts, tool schemas and model it started with, or migrates through an explicit step. Mechanism classes — deterministic workflow execution over an event history, an event-driven harness decoupled from agent logic, a lightweight runtime with automatic recovery — are interchangeable when they meet these rules; verify current options at design time.
- **Recovery** escalates tool → step → run as alternatives under one retry budget, never as nested retries; past the budget, the run hands off to the sized escalation queue (`ai/protocol.md`).
- **Long-horizon handoff.** A run that can outlive one context window keeps its plan, progress log and acceptance checklist in durable, inspectable artifacts, starts each session with a deterministic orientation step (read the plan, progress log and recent changes; run the smoke checks), and works one verifiable unit at a time; tool and test output is short and structured for model consumption. Forcing question: if this run is killed now, can a fresh agent resume from the artifacts alone, and how would it know it is done? *Break when* the task finishes inside one window.
- **"Done" is verified state,** checked against acceptance criteria fixed before work began — which the agent cannot edit — by a component other than the producer: a deterministic check, or a separate, skeptical grader with direct access to the artifact's behavior (validated per `ai/evals.md`). Self-critique in the same context is not verification. *Break when* the work sits well inside model capability: ablate the evaluator — a weak or gameable grader is worse than none.
- **Background agents are jobs, not chats.** A trigger (event, schedule, channel) starts a durable run with explicit stop conditions — a goal check by an independent grader plus token and time budgets — that ends with an artifact and a report. Human touchpoints are asynchronous and batched; interrupts are a scarce budget, measured per task. Forcing question: what ends this run if the goal is never met, and who is told? *Break when* the work is interactive and latency-sensitive (stay synchronous) or the scope is ambiguous (a human-written spec first); goal loops without fast deterministic checks converge on plausible junk.

## Oversight mechanics

The autonomy level per action class is set in `ai/protocol.md`; who may approve what, approval integrity, the kill switch and credential revocation are enforced per `ai/security.md`. The harness supplies the mechanics:
- **Approval is a durable wait, not polling:** persist the run's state, notify the approver, resume via callback.
- **Interrupt** in one step at any point. Each action declares its stop semantics — what a stop leaves behind and which completed steps need compensation — so an interrupted run ends resumable or cleanly stopped.
- **An activity ledger** a human can read — every tool call with its inputs, outputs, decision and actor — plus check-ins the agent itself initiates when it meets ambiguity or a boundary.

## Red flags

- 🔴 The loop executes whatever the model proposes, or one free-form query or shell tool carries the whole safety burden.
- 🟠 Multi-agent justified by role names, without a token-matched single-agent baseline, or with shared mutable state and no single writer.
- 🟠 The agent declares itself done, or can edit its own acceptance criteria.
- 🟠 Run state only in an executor's memory, a provider's server-side conversation or the transcript — nothing resumes after a crash.
- 🟠 Tool errors returned as data, or harness policy that exists only as prompt prose.
- 🟡 A network protocol between components in one codebase and trust domain, or a framework silently owning context policy or permissions.
