# Dependencies and delivery

Native libraries, binaries versus over-the-air updates, Continuous Native Generation (CNG), permissions, upgrades, monorepos.

## Before adding a dependency

Answer in the change description:
- Does the platform, the Expo SDK or an installed library already do it?
- Does it support the New Architecture? `npx expo-doctor` checks installed packages against React Native Directory.
- Does it ship a config plugin, or need native edits?
- Do its releases keep up with your RN version?
- Does it need `ios.privacyManifests` entries (Apple's required-reason APIs), or change your App Store privacy label or Play Data safety form?

In Expo projects, install with `npx expo install`: it picks the version your SDK supports.

## Binaries and over-the-air updates

**Default.** A native change (a new or upgraded native library, a config-plugin change, a native edit) needs a new binary: it runs in Expo Go only if Expo Go bundles that code, and never ships over the air. With expo-updates, a fingerprint runtime version ties updates to compatible binaries:

```json
{ "expo": { "runtimeVersion": { "policy": "fingerprint" } } }
```

**Why.** An update that reaches a binary without its native code crashes; the fingerprint changes with anything native, so such an update never matches an old binary.
**Break:** a project with its own runtime-version scheme (`appVersion`, or manual) keeps it, if every native change bumps it.

**Who gets a fix, when.** JS only: an update, which users on the matching runtime get on the launch after it downloads. Urgent fixes arrive sooner only if the app already checks when it returns to the foreground (`checkForUpdateAsync`, `fetchUpdateAsync`) and reloads (`reloadAsync`) at a safe point (no unsaved input, not mid-flow) or after a prompt. Native code, permissions, config plugins and the updater's own settings: a binary, after store review and as users upgrade. Config and API behavior: the server, for everyone, now. A defect in installed binaries needs a server or OTA mitigation beside the binary fix; say which users each path leaves exposed, and for how long.

**Release in stages.** A store binary cannot be rolled back, only halted: use App Store phased release or a Play staged rollout and widen while crash-free users, terminations (OOM, watchdog), ANR rate and launch time hold; stage updates too (`eas update --rollout-percentage`, `eas update:rollback`). Upload dSYMs, R8 mappings and each update's source maps. Old binaries stay installed for months: API changes stay readable by the oldest supported one, and a server-side minimum version forces upgrades.

## Continuous Native Generation

Under CNG, `ios/` and `android/` are generated by `npx expo prebuild` and not committed, so native configuration goes through config plugins (build settings: `expo-build-properties`); hand edits vanish on the next prebuild. Custom native code, or a thin wrapper whose library lags your RN version, goes in a local Expo module (`npx create-expo-module@latest --local`). Never commit the generated folders to land one tweak: every later SDK upgrade becomes a manual native merge.
**Break:** projects that already commit their native directories edit them directly and keep the app config in sync (`npx expo-doctor` reports drift).

**Permissions:** set each iOS purpose string through the library's config plugin (a missing one crashes the app on first access); ask at the moment of use; send users who blocked the permission to `Linking.openSettings()`.

## Upgrades

**Plan** (≤400 words plus the table unless the caller sets a length, no material finding dropped; omit parts that do not apply): a row per native dependency (package · current → target · New Architecture support · keep, bump, replace or drop · binary or OTA); the steps below, each gated; minimum-OS and toolchain changes (Xcode, JDK, Android Gradle Plugin, Play target API) and the users they drop; the release order.

One Expo SDK per step (bare RN: the Upgrade Helper diff), on its latest patch: read the breaking changes and known issues; `npx expo install --fix`, `npx expo-doctor`; re-check patches and config plugins; a new development build; the main flows on both platforms. Legacy-architecture apps first switch to the New Architecture on SDK 54, the last SDK that allows the legacy one. No feature work on the upgrade branch. An upgrade is a new runtime: ship its binary before any update from it; hotfix older binaries from the pre-upgrade branch.

## Monorepos

- Native dependencies go in the app's `package.json`: a build compiles one version of each. RN CLI autolinks only direct dependencies; Expo autolinking also resolves transitive ones from SDK 54, and aligns Metro with it in monorepos from SDK 55.
- Shared packages list native libraries as `peerDependencies` (plus `devDependencies` for their own tooling), never `dependencies`, which install a second copy.
- Exactly one `react` and one `react-native` per app (`<pm> why react-native`): duplicates fail at runtime.
- One version of each dependency across the workspace; pnpm 11+ reads `overrides` and catalogs only from `pnpm-workspace.yaml`, not the `pnpm` field of `package.json`. In Expo apps, keep the ranges `npx expo install` writes.
